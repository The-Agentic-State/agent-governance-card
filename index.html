The Agent Governance Card

State governments are moving past chatbots into agentic AI — software that takes actions: it uses tools, touches data, sends things, files things, completes multi-step tasks with real autonomy. The governance machinery states rely on today — intake, security review, procurement, audit — was not built for software that acts. What's missing is not another framework; it's a simple, per-deployment record of the questions every state has to be able to answer before an agent goes live: what is it allowed to do, what does it touch, who answers for it when it acts, how does a person step in — and what does it cost to leave.

The Agent Governance Card is that record. A product team completes it before an agentic system gets production access to state data, tools, or users. It is a snapshot of what is true at go-live, not a list of promises; unknown and not in place are formal answers, because a missing mechanism recorded plainly is a governance finding, not a failure. From the team's own answers the card computes an Impact Level that routes proportionate obligations — and when several states fill the same card, their deployments become comparable.

We do it with two instruments:

Instrument 1 · the record

The schema

One canonical, machine-readable file is the source of truth: the explicit metadata a state needs to know about every agent — 44 plain-language questions in 12 dimensions, a 9-field controlled spine for cross-state comparability, an explicit public layer (what citizens get to see), and the derivation rules that compute the Impact Level. Built on OMB M-25-21/22, UK ATRS, NIST, and the agentic standards work — and stress-tested against 20 real deployments before we ask anyone to trust it.

Instrument 2 · the way in

The skill

Nobody fills a 44-field form for fun. The skill is an AI interview that navigates the schema for you: plain-language questions one at a time, advice on what each option means in your context, honest handling of unknowns — then it computes your Impact Level and emits the filled card, human-readable and machine-readable. A governance thinking partner, pointed at producing the record.

A voluntary instrument. The card records, computes, and recommends — it never blocks. Its recommendations become gates only where an adopting authority (a state CIO or agency directive) makes a completed card a precondition for production access.

The schema — card v0.3. This is the actual canonical file (YAML, versioned in GitHub), dimension by dimension. Every face of the card — the skill, a form, a document — renders from it. Questions are the content layer, which is editable.

Front matter — adoption, scope, unit of analysis

▶adoption + scope_trigger + unit_of_analysisfront matter 
schema: agent-governance-card
card_version: "0.3"
derivation_contract_version: 2
adoption: >
  Voluntary instrument. to_resolve items are strong recommendations; they become
  gates only where an adopting directive makes the completed card a precondition
  for production access.
answer_statuses: [answered, unknown, not_applicable, not_in_place]
scope_trigger:
  card_required_if: >
    (interacts directly with the public) OR (materially influences a decision-making
    process with effect on the public or state resources), AND takes actions or
    produces outputs beyond returning static search results.
  out_of_scope: >
    embedded commodity features (autocomplete, spell-check, in-app summarization) and
    purely predictive back-office models.
  out_of_scope_boundary_test: >
    M-25-22 §2(b) two-part test: exempt only if (1) widely available to the public for
    commercial use, AND (2) the AI is embedded in a product with substantial non-AI
    purposes. A product used primarily FOR its AI (a licensed copilot) is in scope.
unit_of_analysis:
  one_card: one agent deployment in one operational context.
  platform_pattern: >
    parent card (shared layer) + one deployment addendum per context.

Derived — the Impact Level, computed from the team's own answers

▶impact_derivationtwo outputs; take the higher; never blocks (contract 2)derived 
impact_derivation:
  output_1_omb_high_impact_status:
    from: C7
    high_if: "C7 == high_impact"
    pending_if: >
      C7 == not_yet_determined OR C7 unanswered — the card still completes: the
      final level is the operational tier marked PROVISIONAL (may rise to High
      once determined) + a to_resolve item. Contract 1's block is retired.
  output_2_operational_tier:
    inputs: [C8, C10, C11, C11a, C12]
    high_if_any:
      - "C12 == yes_unresolved"
      - "C10 == acts_without_approval AND (C11 == hard_to_reverse OR severity(C11a) >= serious)"
      - "C8 == sensitive AND C10 == acts_without_approval"
    moderate_if_any_and_not_high:
      - "C8 in [personal_pii, sensitive]"
      - "C10 in [acts_with_approval, acts_without_approval]"
      - "severity(C11a) >= limited AND C10 != informs"
      - "C12 == yes_with_compensating_controls"
    low: otherwise
    unknown_floor: "any unknown operational input -> tier cannot be Low."
  final_level: "higher of output 1 and output 2; pending output 1 -> provisional."
  to_resolve: "welcoming recommendations, never prohibitions (see adoption)."
  reviewer_confirmation: "a Low result for any public-facing agent must be
    confirmed by a named reviewer outside the build team."
  part2_required_for: [moderate, high]
  part2_when_floored: >
    when Moderate ONLY because of the unknown-floor, Part 2 narrows to
    automation_detail + oversight (E6-E12): honesty costs ~7 questions, not 19.
  high_additionally_requires:   # full OMB M-25-21 §4(b) minimum-practice set
    [pre_deployment_testing, ai_impact_assessment, independent_review,
     ongoing_monitoring_with_periodic_human_review, operator_training,
     tested_failsafe_killswitch, appeal_contest_route,
     user_public_feedback_channel, named_senior_signoff]
comparability_spine: [impact_level, C4, C5, C8, C10, C11, C11a, C17, C18]
public_layer: [C1, C2, C3, C15, C4, C10, impact_level, C14, C17, C18, C21, C22, E13, E14]

The canonical file lives in the repo at schema/agent-governance-card.schema.yaml (with a JSON mirror and a drift-checking build). A filled card is a small values file against it — which is what makes deployments comparable across states.

Three ways to run the card.

1 · In this pageTry it here

The scripted demo below — the real v0.3 questions and the actual derivation engine, ported line-for-line from the skill. Deterministic, works offline. Assumes your system is in scope; the real interview checks scope first.

2 · Live in the browserLive interview (bring a key)

The real conversational skill — paste an OpenRouter key and a model conducts the interview and advises, while the Impact Level is still computed by this page's pinned engine, never by the model.

3 · In your own agentInstall the skill in your agent

One command installs the real skill into your favourite coding agent (Claude Code, Codex, Cursor, and many others) — then ask it to fill in the governance card. The skill drives the interview from the canonical schema and computes the level with the bundled deterministic engine; it works standalone (bundled snapshot).

npx skills add The-Agentic-State/agent-governance-card

Open source (CC-BY-4.0): github.com/The-Agentic-State/agent-governance-card — schema + skill.

Route 2 — go live. Paste an OpenRouter API key, pick a model, and the interview becomes the real conversational skill — straight from this page, no server anywhere.

The key is stored only in this browser (localStorage) and calls go directly from your browser to OpenRouter — there is no server in between. Conversation content is sent to OpenRouter and the model's provider, so use demo agents, not sensitive details. The Impact Level is always computed by the page's pinned engine (derivation contract 2), never by the model.
